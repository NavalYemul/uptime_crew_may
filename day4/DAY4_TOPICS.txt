MODULE 1: LANGGRAPH BASICS & PROMPT ENGINEERING
Source: src/day4/langgraph_basics.py, src/day4/prompt_engineering.py
Notebook: notebooks/01_langgraph_basics.ipynb
-------------------------------------------------

TOPIC 1: StateGraph & TypedDict State
What it is:
  The core LangGraph building block. A TypedDict defines the state that flows
  through the graph. Each node receives the full state and returns a partial dict.
  LangGraph merges updates automatically.
Code reference: src/day4/langgraph_basics.py — BMIState, build_bmi_graph()
Test reference: tests/test_langgraph_basics.py — TestBMIGraph

TOPIC 2: Nodes and Edges
What it is:
  Nodes are Python functions (sync or async). Edges connect them. set_entry_point()
  sets the first node. add_edge() creates fixed connections. compile() builds the
  runnable. invoke() runs with initial state.
Code reference: src/day4/langgraph_basics.py — build_bmi_graph, build_review_graph
Test reference: tests/test_langgraph_basics.py — TestBMIGraph::test_graph_nodes

TOPIC 3: Conditional Routing with add_conditional_edges
What it is:
  Route to different nodes based on state. A routing function returns a string key
  that maps to a node name. Enables branching logic — e.g. "positive" → reply_positive.
Code reference: src/day4/langgraph_basics.py — build_review_graph (sentiment routing)
Test reference: tests/test_langgraph_basics.py — TestReviewGraph

TOPIC 4: Zero-shot, Few-shot, and Chain-of-Thought Prompting
What it is:
  Zero-shot: describe the task with no examples. Few-shot: provide 2-5 input/output
  examples. Chain-of-thought: add "Think step by step" to improve reasoning.
  CoT particularly helps with math, logic, and multi-step problems.
Code reference: src/day4/prompt_engineering.py — zero_shot_prompt, few_shot_prompt, chain_of_thought_prompt
Test reference: tests/test_prompt_engineering.py — TestPromptTemplates

TOPIC 5: Token Counting and Context Window Limits
What it is:
  LLMs process tokens (word fragments). tiktoken counts tokens before sending to
  the API. Staying within context limits avoids truncation. Approx limits:
  GPT-4o 128K, Claude 3.5 Sonnet 200K. Cost = input_tokens × price_per_token.
Code reference: src/day4/prompt_engineering.py — count_tokens, estimate_cost
Test reference: tests/test_prompt_engineering.py — TestTokenCounting


MODULE 2: TOOLS, AGENTS, GUARDRAILS & STRUCTURED OUTPUTS
Source: src/day4/tools_agents.py
Notebook: notebooks/02_tools_agents.ipynb
-------------------------------------------------

TOPIC 6: @tool Decorator
What it is:
  Converts a Python function into a LangChain tool. Docstring becomes description.
  Type hints become JSON schema. The LLM uses the schema to decide when and how
  to call the tool.
Code reference: src/day4/tools_agents.py — calculator, get_weather, search_web
Test reference: tests/test_tools_agents.py — TestTools

TOPIC 7: BaseTool Subclass
What it is:
  For full control: subclass BaseTool and define name, description, args_schema
  (a Pydantic model), and _run(). Useful when you need custom validation logic
  or async support via _arun().
Code reference: src/day4/tools_agents.py — (WeatherTool pattern in notebook 02)
Test reference: tests/test_tools_agents.py — TestWeatherOutput

TOPIC 8: Pydantic BaseModel for Tool Schemas
What it is:
  Use Pydantic models to define typed, validated tool inputs and outputs.
  Alongside Instructor, this enforces structure on LLM responses.
  WeatherOutput(city, temperature, unit, description) is a typed return value.
Code reference: src/day4/tools_agents.py — WeatherOutput
Test reference: tests/test_tools_agents.py — TestWeatherOutput

TOPIC 9: Instructor Library for Structured Outputs
What it is:
  Instructor patches the OpenAI/Anthropic client so the LLM response is
  automatically validated and parsed into a Pydantic model. No regex, no
  string parsing — the LLM is forced to return valid structured data.
  Usage: instructor.patch(client).chat.completions.create(response_model=MyModel)
Code reference: src/day4/prompt_engineering.py — PersonInfo, extract_person_info_mock
Test reference: tests/test_prompt_engineering.py — TestPersonExtraction

TOPIC 10: ReAct Agent (Reason + Act)
What it is:
  The LLM alternates: Thought → Action (tool call) → Observation (result) → repeat.
  Implemented in LangGraph with ToolNode + tools_condition + add_messages reducer.
  LangChain: create_react_agent + AgentExecutor (older pattern).
Code reference: src/day4/tools_agents.py — build_tool_agent, AgentState
Test reference: tests/test_tools_agents.py — TestToolAgent

TOPIC 11: Plan-and-Execute Agent
What it is:
  The LLM generates a full numbered plan first. Then executes each step in order.
  Better than ReAct for long structured tasks where the steps are known upfront.
Code reference: src/day4/tools_agents.py — build_plan_execute_agent
Test reference: tests/test_tools_agents.py — TestToolAgent

TOPIC 12: Guardrails and Safety
What it is:
  Input validation before passing to LLM or tools. Check for prompt injection
  patterns ("ignore previous instructions", "jailbreak", "DAN mode").
  add_guardrails() wraps any function with a safety check layer.
Code reference: src/day4/tools_agents.py — add_guardrails, UNSAFE_PATTERNS
Test reference: tests/test_tools_agents.py — TestGuardrails


MODULE 3: MEMORY & PERSISTENCE
Source: src/day4/memory_persistence.py
Notebook: notebooks/03_memory_persistence.ipynb
-------------------------------------------------

TOPIC 13: Short-term vs Long-term Agent Memory
What it is:
  Short-term: in-process list, lasts for current conversation (sliding window).
  Long-term: persisted to DB or vector store, available across sessions.
  ShortTermMemory: add, get_recent(n), clear. LongTermMemory: store, retrieve, search.
Code reference: src/day4/memory_persistence.py — ShortTermMemory, LongTermMemory
Test reference: tests/test_memory_persistence.py — TestShortTermMemory, TestLongTermMemory

TOPIC 14: ConversationBufferMemory Concept
What it is:
  The simplest form of memory: keep ALL previous messages in a list.
  build_buffer_memory_chain() demonstrates the concept as a plain Python function.
  Limitation: grows without bound. Window/summary variants solve this.
Code reference: src/day4/memory_persistence.py — build_buffer_memory_chain
Test reference: tests/test_memory_persistence.py — TestChatbotGraph

TOPIC 15: MemorySaver (InMemorySaver) and thread_id
What it is:
  compile(checkpointer=MemorySaver()) gives LangGraph persistent memory within a
  process. thread_id is the conversation key — each user gets their own thread.
  Different thread_ids are completely isolated.
Code reference: src/day4/memory_persistence.py — build_chatbot_graph
Test reference: tests/test_memory_persistence.py — TestCheckpointerPreservesHistory

TOPIC 16: State History and Time Travel
What it is:
  Every invoke() creates a checkpoint snapshot. get_state_history() returns all
  past states for a thread. You can fork from any snapshot — full time travel.
  SqliteSaver persists checkpoints across process restarts.
Code reference: src/day4/memory_persistence.py — get_state_history
Test reference: tests/test_memory_persistence.py — TestStateHistory


MODULE 4: HUMAN-IN-THE-LOOP (HITL)
Source: src/day4/human_in_loop.py
Notebook: notebooks/04_human_in_loop.ipynb
-------------------------------------------------

TOPIC 17: interrupt() and Command(resume=...)
What it is:
  interrupt() pauses graph execution and saves state to checkpointer.
  The human inspects the state, then resumes with Command(resume=True/False).
  The graph continues from exactly where it paused. Essential for high-stakes actions.
Code reference: src/day4/human_in_loop.py — build_hitl_graph, review_node
Test reference: tests/test_human_in_loop.py — TestApprovalWorkflow

TOPIC 18: Stateful Agent Workflows with Interrupts
What it is:
  interrupt_before=["node_name"] at compile time tells LangGraph which nodes
  to pause before. The human sees the full state (including draft_action)
  and decides. ApprovalWorkflow wraps submit/approve/reject into a clean API.
Code reference: src/day4/human_in_loop.py — ApprovalWorkflow
Test reference: tests/test_human_in_loop.py — TestApprovalWorkflow::test_approve


MODULE 5: MULTI-AGENT SYSTEMS & AGENTIC RAG
Source: src/day4/multi_agent.py
Notebook: notebooks/05_multi_agent.ipynb
-------------------------------------------------

TOPIC 19: Multi-Agent Coordination — Supervisor Pattern
What it is:
  One supervisor agent routes tasks to specialist sub-agents. The supervisor
  sees all results and decides what to do next. Subgraphs are independent
  compilable graphs used as nodes in the supervisor graph.
Code reference: src/day4/multi_agent.py — build_supervisor_graph, build_research_team
Test reference: tests/test_multi_agent.py — TestSupervisorGraph

TOPIC 20: Subgraph Composition
What it is:
  Each subgraph (research, writer) is a complete LangGraph that compiles independently.
  The supervisor graph uses them as nodes via .compile() output. Clean separation of
  concerns — each agent has its own state and logic.
Code reference: src/day4/multi_agent.py — build_research_subgraph, build_writer_subgraph
Test reference: tests/test_multi_agent.py — TestResearchSubgraph

TOPIC 21: Agentic RAG Pattern
What it is:
  Retrieve → Grade relevance → Rewrite query if irrelevant → Retrieve again → Generate.
  Max 2 rewrite iterations. Grade node checks if retrieved docs answer the query.
  Rewrite node expands the query. Much higher answer quality than single-shot RAG.
Code reference: src/day4/multi_agent.py — build_agentic_rag_graph, RAGState
Test reference: tests/test_multi_agent.py — TestAgenticRAG


MODULE 6: MCP — FROM CONSUMER TO PRODUCER
Source: src/day4/mcp_integration.py
Notebook: notebooks/06_mcp_integration.ipynb
-------------------------------------------------

TOPIC 22: MCP Server Responsibilities (Tools, Resources, Prompts)
What it is:
  An MCP server exposes three types: tools (callable actions), resources (read-only
  data URIs), and prompts (reusable templates). Clients discover them via tools/list.
  FastMCP makes building servers as easy as adding decorators.
Code reference: src/day4/mcp_integration.py — show_mcp_producer_code
Test reference: tests/test_mcp_integration.py — TestMCPProducer

TOPIC 23: JSON-RPC 2.0 Protocol
What it is:
  The wire protocol for MCP. Every call is {jsonrpc, id, method, params}.
  Every response is {jsonrpc, id, result} or {jsonrpc, id, error}.
  Methods: tools/list (discover), tools/call (execute), resources/read, prompts/get.
Code reference: src/day4/mcp_integration.py — show_json_rpc_example
Test reference: tests/test_mcp_integration.py — TestJSONRPC

TOPIC 24: Wrapping Spring Boot as MCP + tiktoken
What it is:
  Any REST API (Spring Boot, FastAPI, Express) can be wrapped as an MCP tool
  using httpx calls inside @mcp.tool() functions. tiktoken counts tokens before
  sending context to the LLM — prevents exceeding context window limits.
Code reference: src/day4/mcp_integration.py — show_spring_boot_mcp_wrapper, tokenize_and_count
Test reference: tests/test_mcp_integration.py — TestTokenizeAndCount
