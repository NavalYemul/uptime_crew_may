TOPIC 1: StateGraph & TypedDict State
What it is:
  StateGraph is LangGraph's core building block. You define a TypedDict that acts
  as the "memory" flowing through the graph — each node receives the full state
  and returns a partial dict to update it. LangGraph merges updates automatically.
  TypedDict gives you type safety and IDE autocompletion.

Real-world example (Indian context):
  Infosys uses StateGraph for their IT service desk agent where 'TicketState'
  carries ticket_id, priority, category, assigned_team, resolution across 8 nodes.
  Each node updates only its relevant fields — clean separation of concerns.

Code reference: src/day4/langgraph_basics.py:BMIState (TypedDict), build_bmi_graph()
Test reference: tests/test_langgraph_basics.py:TestBMIGraph::test_normal_bmi


TOPIC 2: Nodes — Python Functions as Graph Steps
What it is:
  A node is any Python function with signature (state: MyState) -> dict.
  The returned dict is merged into the state. Nodes do exactly one thing:
  compute, call an API, classify text, run a model, etc. Nodes are pure
  and testable — no graph-specific code needed inside them.

Real-world example (Indian context):
  Swiggy's order pipeline has nodes: validate_order -> check_inventory ->
  assign_delivery_partner -> send_confirmation. Each node is independently
  testable and replaceable without changing others.

Code reference: src/day4/langgraph_basics.py:calculate_bmi(), classify_bmi()
Test reference: tests/test_langgraph_basics.py:TestBMIGraph::test_bmi_calculation


TOPIC 3: Edges — Normal and Conditional
What it is:
  Normal edges (add_edge) always connect node A to node B.
  Conditional edges (add_conditional_edges) call a routing function that
  returns a string — the name of the next node to visit. This lets you
  build if/elif/else branching purely in Python without complex graph DSLs.

Real-world example (Indian context):
  HDFC Bank's loan processing: after credit_score_node, a conditional edge
  routes to: approve_node (>750), review_node (600-750), or reject_node (<600).
  Different underwriters handle each path.

Code reference: src/day4/langgraph_basics.py:route_by_category(), build_bmi_graph()
Test reference: tests/test_langgraph_basics.py:TestBMIGraph::test_overweight


TOPIC 4: START/END and Graph Compilation
What it is:
  START is the entry point — add_edge(START, "first_node") defines where execution
  begins. END marks completion. .compile() validates the graph (detects unreachable
  nodes, missing edges) and returns an object with .invoke(), .stream(), .batch().
  Compilation catches bugs before runtime.

Real-world example (Indian context):
  Wipro's AI testing platform compiles test execution graphs at startup,
  catching configuration errors before running expensive test suites against
  client systems. Fail fast at compile time, not at 2 AM in production.

Code reference: src/day4/langgraph_basics.py:build_bmi_graph() — START/END edges
Test reference: tests/test_langgraph_basics.py:TestBMIGraph::test_graph_has_required_nodes


TOPIC 5: Conditional Routing
What it is:
  Conditional routing is LangGraph's if/elif pattern. A routing function reads
  the current state and returns a string key. The conditional_edges dict maps
  keys to node names. You can route to 2 or 20 different paths — all in pure
  Python, fully testable, fully inspectable.

Real-world example (Indian context):
  Zepto's customer support bot: after NLP intent classification, routes to
  order_support | payment_support | delivery_support | return_support nodes.
  Each path has different tool access and escalation policies.

Code reference: src/day4/langgraph_basics.py:build_review_graph(), route_by_sentiment()
Test reference: tests/test_langgraph_basics.py:TestReviewGraph::test_positive_review

TOPIC 6: @tool Decorator
What it is:
  The @tool decorator converts any Python function into an LLM-callable tool.
  LangChain automatically extracts the function name, docstring, and parameter
  type hints to generate the tool schema that the LLM sees. The LLM reads this
  schema to decide when and how to call the tool.

Real-world example (Indian context):
  PhonePe's payment agent has @tool functions: check_balance(account_id),
  transfer_funds(from_id, to_id, amount), get_transaction_history(account_id, days).
  The LLM reads docstrings to understand what each tool does.

Code reference: src/day4/tools_agents.py:calculator, get_weather, search_web
Test reference: tests/test_tools_agents.py:TestTools::test_calculator_basic


TOPIC 7: ToolNode & tools_condition
What it is:
  ToolNode is LangGraph's built-in executor for tool calls. It reads the
  tool_calls field from the last AIMessage, executes each tool, and appends
  ToolMessage results to the state. tools_condition is a built-in conditional
  edge function: routes to "tools" if tool_calls present, else to END.

Real-world example (Indian context):
  Razorpay's fraud detection agent: LLM decides to call risk_score_tool and
  transaction_history_tool simultaneously. ToolNode executes both, appends
  results, and LLM synthesises a fraud verdict from the combined evidence.

Code reference: src/day4/tools_agents.py:build_tool_agent() — ToolNode, tools_condition
Test reference: tests/test_tools_agents.py:TestToolAgent::test_agent_completes


TOPIC 8: ReAct Agent Loop
What it is:
  ReAct (Reasoning + Acting) alternates: LLM reasons about what to do ->
  calls a tool -> observes the result -> reasons again. The loop continues
  until the LLM decides it has enough information to answer (no more tool_calls).
  In LangGraph: agent -> tools -> agent -> tools -> ... -> END.

Real-world example (Indian context):
  PolicyBazaar's insurance comparison agent: user asks "best health plan for
  family of 4 in Delhi under Rs 15,000/year" -> agent calls search_plans() ->
  calls compare_premiums() -> calls check_hospital_network() -> final answer.

Code reference: src/day4/tools_agents.py:build_tool_agent() — the full loop
Test reference: tests/test_tools_agents.py:TestToolAgent::test_count_tool_calls


TOPIC 9: Streaming Agent Output
What it is:
  LangGraph graphs support .stream() which yields events as they happen:
  each node completion, each token from the LLM, each tool execution.
  This lets you build real-time UIs that show the agent "thinking" rather
  than waiting for the full response. Crucial for production UX.

Real-world example (Indian context):
  MakeMyTrip's travel planning agent streams: "Searching flights..." ->
  "Found 12 options..." -> "Checking hotel availability..." -> "Here's your
  itinerary." Users see progress instead of a 10-second blank screen.

Code reference: src/day4/tools_agents.py:build_tool_agent() — compiled graph supports .stream()
Test reference: tests/test_tools_agents.py:TestToolAgent::test_extract_final_answer

TOPIC 10: InMemorySaver & thread_id
What it is:
  InMemorySaver stores graph state in a Python dict (in-process, not persisted).
  thread_id is a string key that identifies a conversation. All .invoke() calls
  with the same thread_id share and accumulate the same state — the bot remembers.
  Different thread_ids are completely isolated.

Real-world example (Indian context):
  Nykaa's beauty advisor chatbot: each customer gets their own thread_id (customer_id).
  Bot remembers skin type, previous purchases, allergies across the whole session.
  thread_id ensures customer A's data never bleeds into customer B's session.

Code reference: src/day4/memory_persistence.py:build_chatbot_graph(), chat_turn()
Test reference: tests/test_memory_persistence.py:TestChatbotGraph::test_different_threads_isolated


TOPIC 11: Conversation History
What it is:
  The add_messages reducer in the state TypedDict ensures messages accumulate
  rather than overwrite. Each turn appends [HumanMessage, AIMessage] to the list.
  get_conversation_history() reads stored state without running any nodes —
  pure state inspection using graph.get_state(config).

Real-world example (Indian context):
  Urban Company's service booking bot: after 5 turns, the bot knows the customer
  wants AC repair in Gurgaon on Sunday, prefers female technicians, has a 3rd floor
  flat — all from conversation history without repeating questions.

Code reference: src/day4/memory_persistence.py:get_conversation_history()
Test reference: tests/test_memory_persistence.py:TestChatbotGraph::test_history_has_correct_roles


TOPIC 12: Time Travel (get_state_history)
What it is:
  Every .invoke() with a checkpointer creates a new checkpoint snapshot.
  get_state_history() returns all snapshots in reverse chronological order.
  You can replay from any checkpoint by passing its checkpoint_id in config.
  This enables debugging, A/B testing agent strategies, and rollback.

Real-world example (Indian context):
  Meesho's catalog agent: when a product description goes wrong, support can
  "time travel" to the checkpoint before the error, inspect what data was
  available, reproduce the bug, and fix the prompt without affecting live agents.

Code reference: src/day4/memory_persistence.py:get_state_history()
Test reference: tests/test_memory_persistence.py:TestChatbotGraph::test_state_history_has_snapshots


TOPIC 13: SqliteSaver for Persistence
What it is:
  SqliteSaver writes checkpoints to a SQLite file on disk. Unlike InMemorySaver,
  memory persists across process restarts — the bot remembers conversations from
  previous sessions. For production: use PostgresSaver (Supabase, RDS, CloudSQL)
  for multi-instance deployments.

Real-world example (Indian context):
  Ola's driver onboarding assistant: uses SqliteSaver so if the driver closes the
  app mid-onboarding, their progress (documents uploaded, forms filled) is preserved
  when they return. No starting over from scratch.

Code reference: src/day4/memory_persistence.py — SqliteSaver pattern in docstring

TOPIC 14: interrupt() — Pausing Execution
What it is:
  interrupt(value) pauses graph execution at any node and stores the current state
  in the checkpointer. The graph is suspended — not running, not consuming compute.
  Your application code inspects the interrupted state (what action was drafted)
  and displays it to a human for review. Execution resumes with Command(resume=...).

Real-world example (Indian context):
  ICICI Bank's loan agent: after AI analyses credit file and drafts "Approve Rs 40L
  at 8.5%", interrupt() pauses execution. The relationship manager reviews the
  recommendation in their web UI, checks soft factors, and approves or modifies.

Code reference: src/day4/human_in_loop.py:build_hitl_graph() — interrupt() call
Test reference: tests/test_human_in_loop.py:TestHITLGraph::test_submit_returns_draft


TOPIC 15: Command(resume=...) — Continuing
What it is:
  Command(resume=value) is the signal to continue a paused graph. The value
  you pass (True, False, or any data) is returned from the interrupt() call
  in the node. This is how human decisions flow back into the graph.
  Multiple resumes are possible — a multi-step approval workflow can have N interrupts.

Real-world example (Indian context):
  Cognizant's contract review system: AI drafts contract -> interrupt() for legal
  review -> Command(resume={'approved': True, 'changes': [...]}) passes back
  both the decision and any requested modifications for the revision node.

Code reference: src/day4/human_in_loop.py:ApprovalWorkflow._resume()
Test reference: tests/test_human_in_loop.py:TestHITLGraph::test_approve_gives_executed_result


TOPIC 16: Approval Workflow Pattern
What it is:
  The ApprovalWorkflow class wraps the interrupt/resume pattern into a clean API:
  submit() -> approve() or reject(). This is the industry-standard pattern for
  any AI system that takes irreversible actions: submit for review, human decides,
  execute or discard. The pattern works for single or chained approvals.

Real-world example (Indian context):
  Tata Consultancy Services' bulk communications platform: AI drafts email to
  50,000 clients -> ApprovalWorkflow.submit() -> Account Director reviews in
  Slack -> approves -> ApprovalWorkflow.approve() -> email executes. Full audit trail.

Code reference: src/day4/human_in_loop.py:ApprovalWorkflow (dataclass)
Test reference: tests/test_human_in_loop.py:TestHITLGraph::test_reject_gives_rejected_result


TOPIC 17: Breakpoints
What it is:
  interrupt_before=["node_name"] tells LangGraph to interrupt execution before
  a specific node runs. interrupt_after=["node_name"] interrupts after.
  Multiple breakpoints can be set. This is used for review pipelines where
  a human must inspect state at specific checkpoints in the workflow.

Real-world example (Indian context):
  Wipro's AI code review pipeline: interrupt_before=["deploy_node"] means
  a human must review before every deployment. interrupt_before=["test_runner"]
  means a QA engineer reviews the test plan before it executes.

TOPIC 18: Subgraphs
What it is:
  A subgraph is a complete compiled LangGraph used as a node inside a parent graph.
  The parent graph calls subgraph.invoke(sub_state) and treats the result like any
  other node output. Subgraphs enable modularity — build and test agents independently,
  then compose them. Each subgraph has its own state TypedDict.

Real-world example (Indian context):
  Accenture India's research automation: a parent "strategy report" graph has
  research_subgraph, analysis_subgraph, and writing_subgraph as nodes. Each is
  independently developed by different teams and composed at the parent level.

Code reference: src/day4/multi_agent.py:build_research_subgraph(), build_writer_subgraph()
Test reference: tests/test_multi_agent.py:TestResearchSubgraph::test_subgraph_runs


TOPIC 19: Supervisor Pattern
What it is:
  A supervisor is a routing agent that decides which sub-agent to call next
  based on the current state. The supervisor has no domain expertise — it only
  reads the state and routes. After each sub-agent completes, control returns
  to the supervisor which decides the next step or terminates.

Real-world example (Indian context):
  Freshworks' customer support: supervisor reads ticket type and current state.
  Routes to billing_agent (payment issues), tech_agent (product bugs), or
  escalation_agent (VIP customers). Each call returns to supervisor for next decision.

Code reference: src/day4/multi_agent.py:build_supervisor_graph(), build_research_team()
Test reference: tests/test_multi_agent.py:TestSupervisorGraph::test_full_pipeline_runs


TOPIC 20: Agent Handoffs
What it is:
  An agent handoff occurs when one agent explicitly sets the next_agent field
  in state to route control to a specific agent. Unlike the supervisor (which
  always routes), handoffs let agents themselves decide when to pass control.
  Used for specialised escalation patterns.

Real-world example (Indian context):
  Practo's medical AI: general_agent triages the query and sets
  next_agent="cardiologist_agent" or "dermatologist_agent" based on symptoms.
  The specialist agent then takes over with domain-specific tools and knowledge.

Code reference: src/day4/multi_agent.py:SupervisorState (next_agent field), route_supervisor()
Test reference: tests/test_multi_agent.py:TestSupervisorGraph::test_messages_accumulate


TOPIC 21: Parallel Agents (fan-out/fan-in)
What it is:
  Fan-out: one node routes to multiple agents simultaneously. Fan-in: a merge
  node collects all their results. LangGraph supports this via parallel branches.
  5 agents running in parallel complete a task in 1/5th the time of sequential agents.
  Critical for research, analysis, and data collection at scale.

Real-world example (Indian context):
  BigBasket's pricing agent: fans out to 5 city_pricing_agents simultaneously
  (Mumbai, Delhi, Bangalore, Chennai, Hyderabad), each checking local competitor
  prices. Fan-in collects all 5 results for national pricing strategy.

TOPIC 22: What is MCP?
What it is:
  Model Context Protocol (Anthropic, 2024) is an open standard that defines how
  AI models connect to external tools, APIs, and data sources. Instead of writing
  custom integrations for each tool, you run an MCP server that exposes tools via
  a standard JSON-RPC interface. Any MCP-compatible client (Claude, LangChain,
  LangGraph) connects and discovers tools dynamically at runtime.

Real-world example (Indian context):
  Juspay's payments AI: instead of hardcoding Razorpay SDK calls and NPCI API calls,
  they run a Juspay MCP server that exposes process_payment, refund_transaction,
  and check_upi_status as MCP tools. Their LangGraph agent connects to it without
  any payment-specific code in the agent itself.

Code reference: src/day4/mcp_integration.py:show_mcp_setup(), show_mcp_servers()
Test reference: tests/test_mcp_integration.py:TestMCPConcepts::test_show_mcp_setup_returns_code


TOPIC 23: MultiServerMCPClient
What it is:
  MultiServerMCPClient connects to multiple MCP servers simultaneously and
  exposes all their tools as a single flat list. Your agent doesn't know or
  care which server provides which tool — it just sees "read_file", "create_issue",
  "query_postgres" as available tools. Used as an async context manager.

Real-world example (Indian context):
  CRED's financial intelligence agent connects to: database MCP server (user data),
  filesystem MCP server (report templates), and Slack MCP server (notifications).
  MultiServerMCPClient merges all 15+ tools into one list for the agent.

Code reference: src/day4/mcp_integration.py:show_mcp_setup() — MultiServerMCPClient usage
Test reference: tests/test_mcp_integration.py:TestMCPConcepts::test_show_mcp_servers_returns_list


TOPIC 24: Popular MCP Servers
What it is:
  Anthropic and the community maintain a growing catalogue of MCP servers.
  Key ones: @modelcontextprotocol/server-filesystem (read/write files),
  @modelcontextprotocol/server-github (repos, issues, PRs),
  @modelcontextprotocol/server-postgres (SQL queries),
  databricks-labs/mcp-server-databricks (jobs, SQL, notebooks).
  All follow the same standard — swap servers without changing agent code.

Real-world example (Indian context):
  Deloitte India's audit automation: filesystem MCP server reads client documents,
  PostgreSQL MCP server queries financial databases, GitHub MCP server creates
  audit findings as issues. Same LangGraph agent code, three different MCP servers.
  Adding a new data source = add one server config, zero agent code changes.

Code reference: src/day4/mcp_integration.py:show_mcp_servers(), mcp_filesystem_read, mcp_databricks_run_sql
Test reference: tests/test_mcp_integration.py:TestMCPConcepts::test_databricks_server_included
